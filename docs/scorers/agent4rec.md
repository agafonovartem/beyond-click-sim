# Agent4Rec-style scorer

Source: `src/beyond_click_sim/scorers/agent4rec/` (`profiles.py`, `prompts.py`, `yes_no.py`, `regression.py`, `listwise.py`).
Wiring/CLI entry points: `runners/in_distribution/interaction_prediction/methods/agent4rec_yes_no.py` and the analogous `regression_prediction`, `cold_start` runner modules.

This document describes the current implementation only. It does not evaluate whether the design is scientifically valid — see `AGENTS.md` / `issues.md` for that framing.

## 1. What this scorer is

The Agent4Rec-style scorer is a **prompt-based pointwise/listwise response simulator**. Like the plain `LLMInteractionYesNoScorer` (`src/beyond_click_sim/scorers/history/yes_no.py`), it predicts a per-row response (yes/no, rating, or rank) for explicit candidate rows. It is *not* a recommender/policy: it never generates its own candidate set.

What distinguishes it from the plain LLM scorer is the **profile module**, adapted from the [Agent4Rec](https://arxiv.org/abs/2310.10108) paper's "social traits + taste" persona design:

- Instead of showing the model raw interaction history rows (`H1. title: X; genre: Y`), it can show a **role-play persona** built from that history: three social traits (activity / conformity / diversity) derived deterministically from train statistics, and/or a free-text **taste** paragraph generated by a separate LLM call over the user's rating history.
- The persona is embedded in the **system prompt**; candidates are shown in the **user prompt** with no raw per-item interaction history line-by-line (unlike the plain history scorer).

Both traits and taste are optional and independently togglable via `profile_components`.

## 2. File map

| File | Responsibility |
|---|---|
| `profiles.py` | `Agent4RecProfileGenerator` — computes traits, generates/caches taste, builds `Agent4RecUserProfile` objects. |
| `prompts.py` | All Agent4Rec prompt templates (system prompt, forced-items/itemwise/preference/listwise user prompts, taste-generation prompts). |
| `yes_no.py` | `Agent4RecYesNoScorer` (binary interaction/watch decision) and `Agent4RecPreferenceYesNoScorer` (binary positive-preference decision). Response parsers. |
| `regression.py` | `Agent4RecRegressor` — 1-5 rating prediction. |
| `listwise.py` | `Agent4RecListwiseRankingScorer` and `Agent4RecPreferenceListwiseRankingScorer` — direct ranking of a candidate group. |
| `__init__.py` | Public re-exports. |

All scorer classes implement the shared `Scorer` contract (`fit(X, y) -> self`, `score(X) -> pd.Series`) from `scorers/base.py`, plus an extra `build_taste(X)` step (see §4).

## 3. User profile object

```python
@dataclass(frozen=True)
class Agent4RecUserProfile:
    user_id: Any
    taste: str | None = None
    activity_group: int | None = None       # 1, 2, or 3
    conformity_group: int | None = None      # 1, 2, or 3
    diversity_group: int | None = None       # 1, 2, or 3
    activity_description: str | None = None  # resolved text for the group
    conformity_description: str | None = None
    diversity_description: str | None = None
```

One profile is built per user. Which fields are populated depends on `profile_components`.

## 4. Profile module: `Agent4RecProfileGenerator`

Constructed with `profile_components: Sequence[str]`, a subset of `("traits", "taste")` (validated against `AGENT4REC_PROFILE_COMPONENTS`; must be non-empty and duplicate-free).

### 4.1 Social traits (`"traits"` component)

Computed deterministically from the **fitted train rows** (`build_traits(X, y, user_ids=...)`), no LLM call involved. Three traits, each binned into 3 tiers via `_three_tier_group(value, low, high)`:

**Activity** — how many interactions a user has.
- Default source: row count per user within the fit frame (`X.groupby(user_column).size()`).
- Optional override: `activity_counts: Mapping[user_id, int]` — e.g. total raw interaction counts computed from the *full, pre-split* dataset. This exists specifically so activity stays non-degenerate when the fit frame only contains a short cold-start history window (see docstring on `_activity_num`).
- Tier thresholds: 60th and 90th percentile of the activity distribution across users in the fit frame (`p60`, `p90`).

**Diversity** — how many distinct genres a user's history spans, using Agent4Rec's "top-mass" definition (`_agent4rec_diversity_count_by_user`):
1. Count genre occurrences per user across their history rows (`genre_column`, split on `|` or `,`, or parsed as a JSON list).
2. Convert counts to per-user genre probabilities, sort descending (ties broken alphabetically for determinism).
3. Keep genres while cumulative probability mass stays ≤ `AGENT4REC_DIVERSITY_TOP_MASS = 0.80`.
4. Clamp to at least 1 genre for any non-empty history (avoids zero-diversity single-genre users, which the released Agent4Rec logic could otherwise produce).
- Tier thresholds: 33rd/66th percentile (`p33`, `p66`).

**Conformity** — how much a user's ratings deviate from each item's mean rating (only computed if `include_conformity=True`, default `True`; MovieLens uses it, Steam disables it — see §8):
1. Compute per-item mean rating over the fit frame.
2. For every train row, squared deviation `(rating - item_mean_rating)^2`.
3. Average per user → `conformity_deviation`.
- Tier thresholds: 25th/80th percentile (`p25`, `p80`).
- **Low deviation → tier 1** ("Dedicated Follower", ratings track historical consensus); **high deviation → tier 3** ("Maverick Critic").

Thresholds are recorded on `self.trait_thresholds_` and surfaced in `manifest()` for reproducibility. Group→text mappings default to `AGENT4REC_ACTIVITY_DESCRIPTIONS` / `AGENT4REC_CONFORMITY_DESCRIPTIONS` / `AGENT4REC_DIVERSITY_DESCRIPTIONS` (movie wording) but can be swapped, e.g. `AGENT4REC_GAME_ACTIVITY_DESCRIPTIONS` / `AGENT4REC_GAME_DIVERSITY_DESCRIPTIONS` for Steam (conformity has no game variant since it's disabled there).

If `"traits"` is *not* in `profile_components`, `fit()` still creates a bare `Agent4RecUserProfile(user_id=...)` shell per user (no group/description fields) so the taste stage has something to attach to.

### 4.2 Taste (`"taste"` component)

A free-text paragraph, generated once per user by a **separate LLM call**, summarizing genre preferences and what tends to earn high vs. low ratings. This is the direct analog of Agent4Rec's `prompt_modify` persona step.

Requires (validated in `__init__`): `taste_client`, `taste_model`, `taste_cache_path`. Optional knobs: `taste_prompt_version`, `taste_prompt_kind` (`"rating"` or `"playtime"`), `taste_temperature` (default `0.0`), `taste_max_tokens`, `taste_max_attempts` (default `5`), `taste_max_workers` (default `1`).

**Generation, `build_taste(profiles, histories, user_ids)`:**
1. For each requested user, compute a cache key (§4.3) and check the on-disk cache.
2. Cache misses are generated via the LLM, sequentially if `taste_max_workers == 1`, or in parallel via `ThreadPoolExecutor` otherwise.
3. `_generate_taste` retries up to `taste_max_attempts` times on any exception (parse failure, API error) before raising `RuntimeError`.
4. Each successful generation is appended to the JSONL cache immediately (not batched at the end), and the in-memory profile dict is updated with `taste=parsed.taste`.
5. `self.taste_cache_stats_` records `{requested_users, hits, misses, generated, max_workers}` for the manifest.

**Prompt construction** (`_taste_messages`), depends on `taste_prompt_kind`:
- `"rating"` (MovieLens): bucket the user's history titles by their 1-5 rating (`_rating_movies`) and fill `AGENT4REC_TASTE_MODIFY_USER_PROMPT_TEMPLATE`. Requires `rating_column` and `title_column`; raises if a rating falls outside 1-5.
- `"playtime"` (Steam): bucket history titles into `zero` / `low` (1-119 min) / `medium` (120-599 min) / `high` (600+ min) playtime buckets (`_playtime_games`) and fill `AGENT4REC_PLAYTIME_TASTE_USER_PROMPT_TEMPLATE`.
- If `summary_column` is set, each history item's description also appends `genres: ...`, `tags: ...`, `summary: ...` (LLM-generated movie-plot summaries — see §8.4) via `_history_item_description`; otherwise it's just the bare title.

**Response format** the taste-generation LLM is asked to produce:
```
TASTE: <descriptive taste>
REASON: <brief reason>
...
HIGH RATINGS: <conclusion>
LOW RATINGS: <conclusion>
```
Parsed by `parse_agent4rec_modify_taste_response` using the same regex style as the released Agent4Rec code: `re.findall(r"TASTE:(.+)", text)` etc., joined with `"| "`. Raises `ValueError` if no `TASTE:` line is found. Note this is a lenient regex (no anchoring beyond the field name), so it does not itself verify the response otherwise matches the requested structure.

At use time, `_format_agent4rec_taste` post-processes the stored taste string: splits on `"| "`, joins with `"; "`, and does a blunt `.replace("I ", "")` (a naive attempt to convert the model's first-person `"I like ..."` phrasing into a fragment that reads naturally when embedded as `"...your movie tastes are: {taste}"`).

### 4.3 Taste cache

Format: **JSONL** at `taste_cache_path`, one row per generated (user, history) pair.

**Cache key** (`_taste_cache_key`, SHA-256 of a sorted JSON payload) is a function of:
- `user_id`
- `history_item_ids` (the exact ordered tuple of item IDs selected by `select_history_by_user`, see §5)
- `prompt_context` — if `summary_column` is configured, this includes the summary text for each history row, so a taste generated *with* summaries and one generated *without* summaries never collide.

This means: the cache is invalidated automatically if the user's selected history window changes (e.g. different `max_history_items`, different split, different seed) or if summary visibility changes — but it is **not** keyed on `taste_prompt_version`, `model`, or `temperature`. Those are stored as extra fields in each cache row for inspection but do not affect the key, so switching model/temperature/prompt version silently reuses a stale cached taste unless `taste_cache_path` itself differs. In practice `agent4rec_taste_cache_path` (runner-level helper, §8) namespaces cache files by `{dataset}_{dataset_version}_seed{split_seed}_{model_slug}_{taste_prompt_version}{_summary}.jsonl`, so model and prompt-version changes do get a fresh file *as long as callers use that helper* rather than passing a custom `taste_cache_path`.

**Concurrency safety:**
- A per-path `threading.Lock` (process-local) plus an `fcntl.flock` exclusive lock on a sidecar `.lock` file (cross-process) guard cache reads/writes, so multiple runner processes sharing one cache file don't corrupt it.
- Loading (`_load_taste_cache`) tolerates duplicate `cache_key` rows left by older parallel runs — first row wins, later duplicates are silently skipped, rather than failing the run.
- Any malformed line (empty, invalid JSON, missing `cache_key`) raises `ValueError` and fails the run — the cache is treated as append-only truth, not best-effort.

### 4.4 `manifest()`

`Agent4RecProfileGenerator.manifest()` returns a dict recording: `profile_components`, all column names, `include_conformity`, whether activity came from `fit_frame_row_counts` or `external_activity_counts`, `diversity_top_mass`, `trait_thresholds_`, and (if taste is enabled) the full taste config (`client_name`, `model`, `temperature`, `max_tokens`, `max_attempts`, `max_workers`, `prompt_version`, `prompt_kind`, `cache_path`, `cache_stats_`). This is embedded into each run's `manifest.json` by the runner (§8) for provenance.

## 5. History selection

`select_history_by_user` (`scorers/history/selection.py`, shared with the plain LLM scorer) picks, per user, the **last `max_history_items` rows in input/train order** (`select_user_history_positions` in `scorers/constant.py`). `max_history_items=None` keeps the full history; `0` keeps none. This window is what taste generation reads from (§4.2) — it is *not* used to build a textual history block for the scored prompt itself (Agent4Rec's user prompt shows only candidates, not raw history — see §6).

## 6. Prompt construction (`prompts.py`)

### 6.1 System prompt — `agent4rec_system_prompt`

Built from whatever profile parts are present (`taste`, `activity`, `conformity`, `diversity`); wording branches on whether any trait is present:

- **No traits, taste only** (or neither — see §7): a short "Assume you are a user browsing {domain} recommendation system... Your {taste_label} are: {taste}." For the default MovieLens wording (`domain_name="movie"`, `taste_label="movie tastes"`) this reuses the exact original Agent4Rec "forced items" prefix (`AGENT4REC_FORCED_ITEMS_SYSTEM_PROMPT_TEMPLATE`); other domains get a generic template.
- **Any traits present**: the fuller "You excel at role-playing..." persona block, listing whichever of activity/conformity/diversity are non-empty, each followed by trait explanation sentences, and (if taste is also present) an extra "Beyond that, your {taste_label} are: {taste}." clause appended at the end.

So the system prompt content — and therefore what the model is told about the user — varies purely based on which `profile_components` were requested and whether taste generation actually produced non-empty text for that user.

### 6.2 User prompt variants

All variants show only the **candidate list**, never raw interaction history rows (that's the key structural difference from the plain history-based LLM scorer):

| Template | Used by | Output contract |
|---|---|---|
| `AGENT4REC_FORCED_ITEMS_USER_PROMPT_TEMPLATE` (`agent4rec_user_prompt`) | `Agent4RecYesNoScorer`, `prompt_style="batch"` | One line per candidate: `ID: Ck; MOVIE: <name>; WATCH: yes/no; REASON: ...` |
| `AGENT4REC_ITEMWISE_USER_PROMPT_TEMPLATE` (`agent4rec_itemwise_user_prompt`) | `Agent4RecYesNoScorer`, `prompt_style="itemwise"` | Bare `yes` or `no`, no reason, one candidate per call |
| `AGENT4REC_PREFERENCE_USER_PROMPT_TEMPLATE` (`agent4rec_preference_user_prompt`) | `Agent4RecPreferenceYesNoScorer` | Same line format but `PREFERENCE: yes/no` against an explicit `target_description` instead of "would you watch" |
| `AGENT4REC_LISTWISE_USER_PROMPT_TEMPLATE` (`agent4rec_listwise_user_prompt`) | `Agent4RecListwiseRankingScorer` | Full ranked permutation of candidate IDs, one per line, with an explicit self-check instruction and a "first character must be C" anchor to reduce preamble |
| `AGENT4REC_PREFERENCE_LISTWISE_USER_PROMPT_TEMPLATE` | `Agent4RecPreferenceListwiseRankingScorer` | Same ranking contract but ranked by "would meet the positive-preference target" |
| `AGENT4REC_RATING_USER_PROMPT_TEMPLATE` (`agent4rec_rating_user_prompt`) | `Agent4RecRegressor` | `RATING: [1-5]` for a single candidate |

Each user-prompt builder also picks an instruction sentence: **"You only watch movies which align with your taste."** when a taste string is present, vs. **"Judge each movie using your available profile and the candidate information."** when it isn't (traits-only case) — see `_AGENT4REC_TASTE_USER_INSTRUCTION` vs. `_AGENT4REC_PROFILE_USER_INSTRUCTION` branching in every builder.

### 6.3 Candidate description formatting

Each candidate row is rendered by `_format_item_description` (in `yes_no.py` / `regression.py`) by concatenating configured columns:
- First configured column with a value becomes the "primary" `<- {value} ->` token (no label); subsequent columns are labeled `<- {label}:{value} ->`.
- `column_labels: dict[str, str]` renames columns for the prompt (e.g. a *history-item-rating-mean* column is relabeled `"History ratings"` for ml-1m — see §8's `PREFIXED_ITEM_RATING_MEAN_COLUMN`; this is how an item's population mean rating gets exposed to the model as a numeric prior, distinct from the user's own taste/traits).
- `json_list_columns: tuple[str, ...]` marks columns whose string value should be `json.loads`'d and rendered as a comma-joined list (used for Steam's `item_genres_json` / `item_tags_json`).
- Numeric values are formatted via `_format_prompt_value`: integers as bare ints, floats truncated to 2 decimals if non-integral, else as ints.
- Missing/NaN/empty values are dropped from the description entirely (no `column: None` noise). If every configured column is empty, falls back to the literal string `"<- no item description ->"`.

## 7. Scorer classes

All scorer `__init__` signatures accept a `profile_generator: Agent4RecProfileGenerator | None` (defaults to one with `profile_components=("traits",)` if omitted — i.e. **taste is opt-in, traits is the default profile mode**), plus `candidate_description_columns`/`item_description_columns` (required, non-empty), `user_column`, `max_history_items`, `temperature`, `max_tokens`, `column_labels`, `extra_body` (passed through to the chat completion call, e.g. vLLM's `chat_template_kwargs`).

### 7.1 Lifecycle: `fit` → (optionally) `build_taste` → `score`

```python
scorer = Agent4RecYesNoScorer(client, model, profile_generator=pg, candidate_description_columns=(...))
scorer.fit(X_train, y_train, profile_user_ids=eval_user_ids)   # builds traits (if enabled) from train rows
if "taste" in pg.profile_components:
    scorer.build_taste(X_eval)                                 # separate explicit stage, LLM calls
scores = scorer.score(X_eval)
```

`fit()`:
- If `"traits"` in `profile_components`: calls `profile_generator.build_traits(X, y, user_ids=profile_user_ids)`. Raises if any requested user has zero train rows (`"No train rows for requested Agent4Rec profile users"`).
- Else: builds empty profile shells for the requested (or all) users.
- If `"taste"` in `profile_components`: selects history windows (§5) for those users via `select_history_by_user`, stored on `self.history_by_user_`. Taste itself is **not** generated here — that is deliberately deferred to `build_taste()`, so callers can fit once and reuse the fitted state across differently-scoped eval calls without re-triggering LLM taste generation each time (per the docstring in `yes_no.py:101`).

`build_taste(X)`: resolves the user set present in `X`, calls `profile_generator.build_taste(profiles=self.profile_by_user_, histories=self.history_by_user_, user_ids=...)`.

`score(X)` fails fast (`RuntimeError`) if taste is a configured component but any user in `X` has an empty/missing `.taste` — i.e. you cannot `score()` before `build_taste()` when taste is enabled (`_require_taste_for_users`).

### 7.2 `Agent4RecYesNoScorer` — binary watch/interact decision

`score(X)` requires `candidate_group_column` grouping and exactly one user per group. Two prompt styles:

- **`prompt_style="batch"`** (default): every candidate in a group is scored with **one** LLM call. The response must contain a line per candidate ID matching the `ID: Ck; MOVIE: ...; WATCH: yes/no; REASON: ...` contract, parsed by `parse_agent4rec_watch_response` → `_parse_agent4rec_binary_response`.
- **`prompt_style="itemwise"`**: every group must contain exactly one row (raises otherwise); one LLM call per candidate, expecting a bare `yes`/`no` (`parse_single_yes_no_response`) — no explanation, cheaper per call but N calls instead of 1 per group.

`_parse_agent4rec_binary_response` (regex-based, `re.IGNORECASE | re.DOTALL`):
- Matches `ID: Ck` (optionally preceded by `ID:`/`LABEL:`), then `MOVIE:`/`GAME:`/`ITEM:` field, then the decision field (`WATCH:` or `PREFERENCE:`), then `REASON:` up to the next candidate ID or end of text.
- Strict validation: unknown labels → `ValueError`; duplicate labels → `ValueError`; missing labels (any expected `Ck` absent from the response) → `ValueError`; a decision value that isn't exactly `yes`/`no` → `ValueError`. There is no silent fallback — a malformed response fails that candidate group's score entirely (handled upstream by the runner's retry loop, §8).

### 7.3 `Agent4RecPreferenceYesNoScorer` — binary preference-target decision

Subclasses `Agent4RecYesNoScorer`, overrides the user-prompt builder to use `agent4rec_preference_user_prompt` with an injected `target_description` (a caller-supplied string describing what counts as a "positive preference" for the specific target being simulated, e.g. "the user would give this movie a rating of 4 or 5"), and the parser to expect `PREFERENCE: yes/no` instead of `WATCH: yes/no`. `target_description` must be non-empty at construction.

### 7.4 `Agent4RecRegressor` — 1-5 rating prediction

One LLM call **per row** (not grouped/batched — no `candidate_group_column` concept here). Requires `target_description` (what the rating question means) and `valid_values: Sequence[int]` (integers only, e.g. `range(1, 6)`).

`parse_agent4rec_rating_response`: accepts either a bare integer response or a `RATING: k` line; rejects multiple `RATING:` matches; validates the parsed integer is in `valid_values`, else raises. Returns `float(value)`.

### 7.5 Listwise ranking scorers (`listwise.py`)

Both subclass `Agent4RecYesNoScorer` and reuse all of its `fit`/`build_taste`/history/profile machinery — only the user-prompt builder and response parser change.

- **`Agent4RecListwiseRankingScorer`**: asks the model to output the *entire* candidate-ID permutation, most-to-least likely to watch. Uses the shared `parse_ranked_labels_response` (`scorers/history/listwise.py`) which extracts all `Ck` tokens via regex, validates no unknowns/duplicates/missing IDs. Scores are then assigned as `len(ranked) - rank` (rank 1 = highest score), i.e. this converts an ordinal ranking into a pseudo-score compatible with the same ranking-metric pipeline used by pointwise scorers.
- **`Agent4RecPreferenceListwiseRankingScorer`**: same idea but ranks by "would meet the positive-preference target" using `target_description`, non-empty required.

Note both listwise scorers still route through `Agent4RecYesNoScorer.score()` — the group-level control flow (one user per group, batch call, parsing) is identical; only `_build_user_prompt`/`_parse_response` are overridden. `prompt_style="itemwise"` is not meaningful for these (ranking inherently needs all candidates in one call) — nothing in the code currently guards against setting it, so it would silently behave like a single-item "rank of 1" degenerate case if misconfigured (`prompt_style` on the base class still governs it since these subclasses don't override `score`/`_build_itemwise_messages`).

## 8. Runner-level wiring (`runners/.../methods/agent4rec_yes_no.py`)

The scorer classes are dataset-agnostic; per-dataset configuration lives in the runner as parallel dicts keyed by `dataset_name` (`"ml-1m"` / `"steam"`):

| Dict | Purpose |
|---|---|
| `DATASET_CANDIDATE_COLUMNS` | Default candidate description columns. ml-1m: `(item_title, PREFIXED_ITEM_RATING_MEAN_COLUMN, item_genres)` — i.e. title, the item's historical mean rating, and genres. Steam: `(item_title, item_genres_json, item_tags_json)`. |
| `DATASET_COLUMN_LABELS` | Prompt labels for those columns, e.g. `PREFIXED_ITEM_RATING_MEAN_COLUMN → "History ratings"`. |
| `DATASET_JSON_LIST_COLUMNS` | Which columns need JSON-list parsing before rendering (Steam's genre/tag JSON columns). |
| `DATASET_PROFILE_GENERATOR_KWARGS` | Steam overrides: alternate genre/tag/title/playtime columns, `include_conformity=False` (no 1-5 rating signal to compute conformity from), `taste_prompt_kind="playtime"`, game-flavored activity/diversity description dicts. |
| `DATASET_PROMPT_KWARGS` | Domain wording overrides for Steam: `domain_name="game"`, `taste_label="game tastes"`, `entity_field="GAME"`, `entity_name="game"`, `entity_plural="games"`. |
| `DATASET_SUPPORTS_TASTE` | Both currently `True`. |
| `DATASET_TASTE_PROMPT_VERSION` | Version tag baked into the cache filename. |

`run_method(...)` is the actual orchestration entry point invoked by task-specific runner scripts (e.g. the `run_ml1m_qwen36_27b_local_parallel.py` runner covered earlier in this session). Key behavior beyond what's already described:

- **`summary_usage`** (`"none" | "profile" | "candidate" | "both"`, resolved via `resolve_agent4rec_summary_usage`): controls whether the LLM-generated movie-plot summary column (`ITEM_SUMMARY_COLUMN`, only available for ml-1m) is appended to (a) the taste-generation prompt's history items (`"profile"`) and/or (b) the scored candidate description (`"candidate"`). `"both"` does both (this is presumably the "sumboth" strategy referenced in recent commits). Requesting `"profile"`/`"both"` without `"taste"` in `profile_components` raises `ValueError`; requesting any summary usage on a non-ml-1m dataset raises `ValueError`. `task_item_summary_metadata` additionally verifies the task actually carries validated, non-missing summary provenance before allowing use.
- Builds `taste_cache_path` automatically via `agent4rec_taste_cache_path()` when not explicitly passed, namespaced by dataset/version/split-seed/model/prompt-version/summary-flag (see §4.3).
- After scoring, computes **both** a pointwise result (`pointwise_metrics_for_split`, plus a `test_failure_as_negative` variant where unparseable/LLM-error rows count as negative rather than being dropped) and a **ranking** result (`ranking_metrics_for_split`, plus `test_failure_as_zero_group`) from the same scored output — both are always written (`metrics.json` and a ranking metrics file), regardless of which scorer class was used, since candidate groups support both evaluation protocols.
- Writes a full `manifest.json` per run capturing: scorer class/config, `profile_generator.manifest()` (trait thresholds, taste cache stats, etc.), decision-rule/parser contract name, request limits, LLM error count, candidate-group counts (requested vs. successfully scored), task manifest, and the current git commit — this is the run's reproducibility record.
- `_score_groups` (imported from the plain `llm_yes_no` method module) provides the retry-per-group and thread-pool-worker (`max_workers`) execution wrapper shared with the non-Agent4Rec LLM scorer; malformed/erroring groups are captured into `llm_errors.jsonl` rather than aborting the whole run.

## 9. Summary of user-facing options and their effects

| Option | Where set | Effect |
|---|---|---|
| `profile_components` | `Agent4RecProfileGenerator` | `("traits",)`: deterministic persona only, no LLM taste call, cheapest. `("taste",)`: only free-text taste, no activity/conformity/diversity framing, system prompt uses the short "forced items" wording. `("traits", "taste")`: full persona — both trait sentences and taste appended. |
| `include_conformity` | `Agent4RecProfileGenerator` | Whether the conformity trait (rating-deviation-from-item-mean) is computed at all; must be `False` for datasets without a 1-5 rating signal (Steam). |
| `activity_counts` | `Agent4RecProfileGenerator` | Overrides the activity trait's source from "row count in fit frame" to an externally supplied fixed count (keeps activity meaningful under short cold-start histories). |
| `taste_prompt_kind` | `Agent4RecProfileGenerator` | `"rating"` buckets history by 1-5 rating (movies); `"playtime"` buckets by playtime range (games) — changes both the taste-generation prompt and required history columns. |
| `taste_temperature` / `taste_max_tokens` / `taste_max_attempts` / `taste_max_workers` | `Agent4RecProfileGenerator` | Sampling/robustness/parallelism of the taste-generation LLM calls, independent of the main scoring LLM's settings. |
| `summary_column` (via runner `summary_usage`) | `Agent4RecProfileGenerator` | Whether generated movie-plot summaries are folded into taste-generation history items (also changes the taste cache key). |
| `domain_name` / `taste_label` / `entity_field` / `entity_name` / `entity_plural` | scorer `__init__` | Swaps "movie/watch" wording for "game/choose" wording (or any other domain) throughout system+user prompts. |
